# ADR 0003 — SMTP outbox: anti-ghost state machine

Date: 2026-07-17 · Status: accepted

## Context

Phase 2 ([PLAN.md](../PLAN.md) §4) requires "compose, reply, forward; SMTP
send with an 'outbox' queue (never a lost send)", and the concept paper (§1)
adds "never a ghost send". These two rules are in tension:

- **Never lost** pushes toward aggressively retrying any doubtful send.
- **Never a ghost** forbids resending a message whose fate is unknown — a
  crash between the SMTP handoff and the local acknowledgment creates
  exactly this ambiguity, and SMTP offers no idempotent delivery.

A silent duplicate is worse than a delay: a delay can be made up, a
duplicate has already reached the recipient.

## Decision

**1. Persistent journal before any network call.** Every send is written to
the `outbox` table (SQLite) *before* any SMTP connection — the same
contract as the triage action queue. A crash or a cut never loses the intent.

**2. Strict state machine, the ambiguity window narrowed to the handoff:**

```text
queued ──→ sending ──→ sent
   ↑          │
   │          ├─ transient failure ──→ queued (automatic retry)
   │          ├─ permanent refusal ──→ rejected (user decision)
   │          └─ crash in flight ────→ interrupted (quarantine)
   └────────── requeue: explicit user decision
```

A message found in `sending` at the start of a flush comes from a crash: it
is **quarantined (`interrupted`), never resent automatically**. The UI
presents the decision ("Resend" / "Discard") with the warning to check the
Sent folder. The Message-ID, generated by US at composition and persisted
in the journal, makes the send correlatable to the message that actually
went out (an automatic IMAP reconciliation is possible later without
changing the model).

**3. Transient/permanent classification delegated to the adapter.**
`mail-core` defines the `MailTransport` port (`SendError::Transient|Permanent`);
`mail-smtp` (plain, XOAUTH2, smtp.gmail.com:465) classifies: a 5xx response
to the send = refusal of the message (`rejected`, the queue continues);
everything else = transient (back to `queued`, the pump stops — the network
went down, no point insisting). **Authentication is settled at connection
time** (`test_connection` + refresh token and a second attempt on the host
side): an expired token, surfacing as a 5xx over SMTP, can thus never be
mistaken for a permanent refusal of a sound message.

**4. Serialized flush.** Only one pump at a time (desktop-side lock): two
concurrent flushes would each quarantine the sends "in flight" from the
other.

## v1 scope (explicit refusals)

- **Plain text only**; outgoing HTML will come later, if needed.
- **Reply = recipient + Re: + In-Reply-To/References** (a full thread
  References would require storing the References of every received
  message).
- No quoting of the original message, no forwarding, no synced drafts — the
  rest of Phase 2 will cover them.
- Gmail itself places SMTP sends in "Sent": no IMAP APPEND. Other providers
  will require it (Phase 3, multiple accounts).

## Consequences and watch points

- Envelopes synced before this version have neither a raw address nor a
  Message-ID (columns added by migration, NULL value): "Reply" on an old
  message requires a full resync. Acceptable: recent mail is what gets
  replied to.
- `sent` sends stay in the journal (provable history); a purge will come if
  volume justifies it.
- `EmailAddress` now refuses blanks, commas, semicolons and angle brackets:
  closes off header injection and makes storing recipient lists safe by
  construction.
- Tests for the two golden rules in `mail-core::outbox`:
  `queued_send_survives_process_restart`,
  `network_cut_keeps_message_queued_then_next_flush_sends_it`,
  `inflight_message_is_quarantined_never_resent`,
  `user_requeue_is_the_only_way_out_of_quarantine`.
