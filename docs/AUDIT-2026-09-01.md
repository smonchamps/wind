# Audit de code complet — Wind — 2026-09-01

> Revue à regard neuf de TOUTE la base (63 k lignes hors docs/spikes),
> sur la 0.15.0 (`main` = `4712b29`), un jour après l'ouverture de la
> vague bêta 1. Six auditeurs par couche + outillage transversal
> (clippy pedantic/nursery, `npm audit`, greps, churn git), chaque
> constat re-lu et les S1 re-vérifiés à la main (`open` 5.4.1,
> `imap` 3.0.0-alpha.15, `sync.rs`, `commands.rs`, journaux versionnés).
>
> Principe directeur du CE pour les remèdes : **la chose la plus
> simple et la plus sûre qui fonctionne.** Chaque remède ci-dessous
> est le plus court connu ; quand il y a une décision produit, elle
> est marquée **[décision CE]**.
>
> Sévérités : **S1** = perte de données, sécurité, PII, gel du thread
> principal, filet vacant ; **S2** = bug réel, perf mesurable, fragilité ;
> **S3** = propreté, simplicité, dette de lecture. « À confirmer » =
> constat déduit du code, avec le test qui le prouverait.
> « Déjà D-xx » = consigné à [DEBT.md](DEBT.md), non redoublé.

## 1. Constats S1 — à traiter avant tout autre chantier

### S1-1 · Données personnelles de tiers versionnées dans un dépôt PUBLIC
`spikes/demarrage/journaux/{reel,vide,sondes}/*.log` — 36 fichiers,
**9,1 Mo**, commit `051bb01` (2026-08-26). Vérifié : **99 adresses
distinctes** (le CE et des tiers) + aperçus de messages
(`"preview":"…"`). Le registre bêta a été anonymisé pour exactement
cette raison ; ces journaux la contredisent.
**Remède** : `git rm` + réécriture d'historique
(`git filter-repo --path spikes/demarrage/journaux --invert-paths`),
force-push, invalidation des clones/forks (GitHub : demander la purge
du cache au support si le dépôt a été forké) ; puis `*.log` et
`target/` **globaux** au `.gitignore` (le trou : `/*.log` racine seul,
`.gitignore:17`). **[décision CE]** : la réécriture d'historique casse
les clones des cinq testeurs ? Non — ils ont l'installeur, pas le dépôt.

### S1-2 · 17 commandes `async` bloquent hors `hors_pompe`, la garde ne le voit pas
`e2e/main-thread-guard.mjs:100-106` saute toute commande `async`
(`if (estAsync) continue`). Or l'ADR 0019 dit qu'`async` seul déplace
le blocage sur un worker tokio (workers = cœurs). Commandes concernées
(`commands.rs`) : `connect_accounts` 174/204/247, `add_*_account` 344/520,
`reconnect_account` 376, `remove_account` 560/581, `sync_inbox` 951/1039,
`sync_inbox_light` 1077/1168, `message_body` 2047/2132, `save_attachment`
2407/**2419 `std::fs::write`**, `reply_context` 3670, `reply_all_context`
3763, `forward_context` 3833, `flush_outbox` 3956, `sync_apres_geste` 4058,
`fetch_source_attachment` 5170-5245, `sync_drafts` 5299, `backfill_bodies`
5967, `telecharger_et_lancer` 6269. Aucune ne tient `AppState.commandes` :
`mark_flagged` sous verrou se croise avec `message_body` hors verrou.
**Remède** : étendre la garde (corps d'une commande `async` = uniquement
`hors_pompe(`/`spawn_blocking(` + glue ; tout `Store::open`, `lock_accounts`,
`std::fs`, `auth_for` en dehors = ÉCHEC), la prouver RED, migrer les 17.

### S1-3 · `open_link` lance `powershell.exe` de façon synchrone sur le thread principal
`commands.rs:6136-6145` (exemptée « ShellExecuteW détaché ») ;
`apps/desktop/Cargo.toml:58` `open = "5"` sans feature. Vérifié dans
`open-5.4.1/src/windows.rs:75` : `Command::new("powershell.exe")` +
`Start-Process` ; `ShellExecuteW` n'existe que sous
`shellexecute-on-windows`. Un `CreateProcess` PowerShell (+ Defender)
à chaque clic de lien, sur la pompe (budget 150 ms).
**Remède (1 ligne)** : `open = { version = "5", features = ["shellexecute-on-windows"] }`,
puis mesure `freeze-probe.py`. Corriger le commentaire 6133 et `main-thread-guard:48`.

### S1-4 · Aucune garde mono-instance alors que `main.rs:96-97` nomme le risque
Les verrous `outbox_flush`/`drafts_push`/`bodies_backfill` sont par
processus ; pas de `tauri-plugin-single-instance` (vérifié). Double
lancement = deux vidanges, deux jeux de veilleurs IDLE, doubles bulles,
deux `update_install` (l'installeur NSIS relance avec `/R`).
**À confirmer** : lancer l'exe deux fois, envoyer un message.
**Remède** : plugin single-instance (focus de la fenêtre existante), ou
verrou fichier `fs4` déjà en dépendance, à côté de `wind.db`.

### S1-5 · Veille IDLE : deux lectures non bornées par tour
`crates/mail-imap/src/lib.rs:478-493` (`veiller`) ; vérifié dans
`imap-3.0.0-alpha.15/src/extensions/idle.rs:225-247` : `init()` (envoi
`IDLE`, lecture du `+`) précède la pose du timeout, la sortie fait
`set_read_timeout(None)`, puis `Drop → terminate()` lit la réponse au
`DONE` **sans borne**. Le doc-comment lib.rs:466-476 (« toutes les
lectures bornées ») est contredit. Sur un serveur/NAT qui ACK sans
répondre, le thread veilleur gèle sans erreur ni reconnexion (l'ADR 0018
a mesuré la COUPURE, pas le silence acquitté).
**Preuve** : listener local qui répond `+ idling` puis se tait.
**Remède** : garder un `TcpStream::try_clone()` avant l'enrobage TLS et
re-poser `set_read_timeout(Some(IO_TIMEOUT))` à l'entrée ET à la sortie
de `veiller` (options socket partagées par le clone).

### S1-6 · Boîte vidée = synchro « initiale » : zéro notification, re-téléchargement intégral
`sync.rs:99` `if state.last_uid == 0 { initial_sync }` ; `sync.rs:106`
`last_uid = max_uid` ; `store.rs:3639` `COALESCE(MAX(uid), 0)`. INBOX
archivée à zéro → relève suivante en `SyncMode::Initial` → `notify.rs:50`
ne bulle rien ; `initial_sync` repaie `list_uids` + fetch complet. Le
test `sync.rs:732` fige le mécanisme sans voir la conséquence.
**Test (6 lignes)** : add(1) → sync → expunge(1) → sync → add(2) → sync
⇒ `mode == Incremental`. **Remède** : décider Initial sur « état créé
dans CET appel » (drapeau `synced_once`), jamais sur `last_uid == 0`.

### S1-7 · Une action refusée à jamais bloque le journal d'une boîte à vie, en silence
`sync.rs:229` `Err(_) => break` ; `pending_actions` sans `attempts` ni
`last_error` (`store.rs:141-146`) ; `error.rs:13` `Server(String)` sans
Transient/Permanent (la distinction existe pour SMTP, `transport.rs:17-29`).
Un `MoveTo` vers un dossier supprimé échoue à chaque cycle, retient
TOUTES les actions suivantes de la boîte, `SyncReport` n'a pas de champ
erreur, `faut_relever` (`sync.rs:395`) force la relève à chaque cycle
pour toujours. Le contraire du gate Phase 2 (`action.rs:3-6`).
**Remède** : `attempts` + état `refusee` (patron `outbox.rejected`),
erreur remontée dans `SyncReport`, `Error::Server { kind, detail }`.
Lié : **store.rs:2061-2067** une ligne `pending_actions` illisible
(`kind` inconnu) fait échouer TOUT `pending_actions(mailbox_id)`.

### S1-8 · La CI ne joue pas les tests des exemples, dont celui de non-divulgation d'identifiants
`.github/workflows/ci.yml:43` `cargo test --workspace` (sans
`--all-targets`) vs `.githooks/pre-push:81-89` qui explique pourquoi
`--all-targets` « n'est PAS décoratif ». Le seul filet non contournable
(`--no-verify`) vérifie moins que le hook. **Remède (1 ligne)** :
`cargo test --workspace --all-targets` (+ `--doc`).

### S1-9 · Le hook avale le diagnostic des trois gates textuelles
`.githooks/pre-push:58,63,70` `> /dev/null` alors que les `ECHEC …`
partent sur stdout (`contrast.mjs:111`, `system-coherence.mjs:42`,
`main-thread-guard.mjs:71`). `gate.ps1:5` dit l'inverse.
**Remède** : supprimer les trois redirections.

### S1-10 · `reset_mailbox` et `remove_local` non atomiques : fils fantômes sur crash
`store.rs:1455-1522` (9 DELETE/UPDATE en autocommit puis
`thread::rebuild_account`), `store.rs:1968-2005` (7 DELETE +
`thread::refresh` en autocommit hors `echo.rs`) ; appelants non
enveloppés : `sync.rs:69`, `store.rs:1835-1837` (N×8 fsync par UID),
`store.rs:3532-3536`. Crash entre DELETE et rebuild = `threads` avec
`inbox_size > 0` sans enveloppes : la « pastille devant une liste vide »
déjà payée à E5. **Remède** : `unchecked_transaction` comme
`save_body_full` (S:2124) ; `remove_local` exige la transaction de
l'appelant. Test : injection d'échec dans `rebuild_account` puis
`unified_count == page.len()`.

### S1-11 · D-36 (colonne fantôme `echos`) touche chaque base bêta NEUVE
`store.rs:272` : `\n` dans un commentaire `--` du littéral `SCHEMA`.
Déjà consigné, mais les cinq bases de la vague 1 naissent avec.
**Remède** : un caractère. Test : noms de colonnes d'`echos` sur base neuve.

## 4. Patterns d'architecture

1. **« Un seul cerveau » tenu au niveau du SQL (0 `rusqlite` dans le
   shell, 0 `invoke` hors port), percé au niveau de la POLITIQUE.** Le
   moteur de synchro d'un compte est `run_sync` (313 l.) dans le shell ;
   `frontiere_corps` (« LA frontière du corps riche ») vit dans le shell ;
   `vue_invitation` recalcule ce que le cœur sert ; 12 fonctions pures
   testées in-file dans `commands.rs` (`attente_apres_echecs`,
   `safe_file_name`, `mime_for_name`, `repere_valide`, `nom_normalise`,
   `resoudre_categorie`…) ; l'ordonnanceur de synchro (cadences,
   watchdog, veille, réseau) vit dans `App.svelte` ; le fournisseur
   d'authentification est deviné en JS (`GuichetCompte:47-50`) ; le
   texte d'un mail sortant (réponse iTIP) est fabriqué par l'UI. Le web
   (Phase 4) ne retrouvera rien de tout ça. → `mail-core::sync_account`,
   `releve.rs` (casse le couplage bidirectionnel `veilleur` ↔ `commands`),
   ordonnanceur `tokio` côté shell, `fournisseur(email)` côté cœur.
2. **« Décision pure, exécution ailleurs » (STANDARD §4) appliqué aux
   feuilles, pas au tronc.** `plan_sync` n'existe pas (le choix
   initial/incrémental/reset est inline avec `select` et `replay`) — un
   `plan_sync(state, snapshot) -> SyncPlan` aurait rendu S1-6 testable en
   une ligne ; `flush_outbox` machine à états inline ; `geste_avec_echo`
   décision enfouie dans la transaction ; décision d'arrivée du Portier
   et règle du Non écrites DANS les boucles SQL (`store.rs:1677-1755`).
   Contre-exemples à imiter : `thread::plan`, `plan_draft_pull`, `notify`,
   `crash`, `demenagement.rs`.
3. **`mail-core` est un `store.rs` étalé.** Six modules « métier »
   (`nav`, `echo`, `drafts`, `outbox`, `correspondants`, `search`) sont
   des `impl Store` + SQL en cycle avec le hub (`nav.rs:23-26` importe 9
   fragments SQL de `store`, `store.rs:1544,1560` rappelle `nav`/
   `correspondants`). Le trait `MailServer` mêle capacité et donnée
   (`Option<Vec>` = « pas supporté ») et `Folder` n'a ni délimiteur ni
   SPECIAL-USE (d'où `[Gmail]` deviné). → `store/` en sous-modules
   déclarés pour que l'arbre d'`use` dise la vérité ; `capabilities()`
   séparé ; `Folder { delimiter, special_use }`.
4. **Une connexion SQLite par commande** (107 `Store::open`, rituel
   complet à chaque fois). Le verrou global `commandes` sérialise déjà :
   une connexion partagée dans `AppState` est la forme la plus simple,
   et supprime D-9, D-34 et la moitié de S2-cœur.
5. **Politique d'erreur non typée au port réseau** — `Error::Server(String)`,
   `SendError::Transient(String)` fourre-tout, 332 `map_err → String` dans
   le shell : ni le rejeu (S1-7), ni le refresh OAuth (SMTP martèle
   l'endpoint), ni l'UI ne peuvent décider.
6. **L'UI est un contrôleur** : `App.svelte` orchestre par 10
   `bind:this` et 20 méthodes impératives ; toute vue qu'App ne tient pas
   n'est jamais resservie (D-48). Le store `generation` est le plus
   simple.
7. **Trois piles TLS** et **deux `reqwest`** dans un binaire Windows.
8. **Les gates textuelles gardent des mots-clés, pas des propriétés** :
   `main-thread-guard` s'arrête à `async` ; `startup.spec` ignore
   les sondes absentes ; les coutures `__e2e*` vivent en prod.
