# Complete code audit — Wind — 2026-09-01

> Fresh-eyes review of the ENTIRE codebase (63 k lines excluding docs/spikes),
> on 0.15.0 (`main` = `4712b29`), one day after the opening of
> beta wave 1. Six auditors per layer + cross-cutting tooling
> (clippy pedantic/nursery, `npm audit`, greps, git churn), each
> finding re-read and the S1s re-verified by hand (`open` 5.4.1,
> `imap` 3.0.0-alpha.15, `sync.rs`, `commands.rs`, versioned logs).
>
> The CE's guiding principle for remedies: **the simplest and safest
> thing that works.** Every remedy below is the shortest one known;
> where there is a product decision, it is marked **[CE decision]**.
>
> Severities: **S1** = data loss, security, PII, main-thread freeze,
> vacant net; **S2** = real bug, measurable perf, fragility;
> **S3** = cleanliness, simplicity, reading debt. "To confirm" =
> finding deduced from the code, with the test that would prove it.
> "Already D-xx" = logged in [DEBT.md](DEBT.md), not duplicated.

## 1. S1 findings — to handle before any other job

### S1-1 · Third-party personal data versioned in a PUBLIC repository
`spikes/demarrage/journaux/{reel,vide,sondes}/*.log` — 36 files,
**9.1 MB**, commit `051bb01` (2026-08-26). Verified: **99 distinct
addresses** (the CE and third parties) + message previews
(`"preview":"…"`). The beta registry was anonymized for exactly
this reason; these logs contradict it.
**Remedy**: `git rm` + history rewrite
(`git filter-repo --path spikes/demarrage/journaux --invert-paths`),
force-push, clone/fork invalidation (GitHub: ask support to purge the
cache if the repo has been forked); then `*.log` and
`target/` **global** in `.gitignore` (the gap: root `/*.log` only,
`.gitignore:17`). **[CE decision]**: does the history rewrite break
the five testers' clones? No — they have the installer, not the repo.

### S1-2 · 17 `async` commands block outside `hors_pompe`, the guard doesn't see it
`e2e/main-thread-guard.mjs:100-106` skips every `async` command
(`if (estAsync) continue`). Yet ADR 0019 says that `async` alone only
moves the blocking onto a tokio worker (workers = cores). Commands
concerned (`commands.rs`): `connect_accounts` 174/204/247, `add_*_account`
344/520, `reconnect_account` 376, `remove_account` 560/581, `sync_inbox`
951/1039, `sync_inbox_light` 1077/1168, `message_body` 2047/2132,
`save_attachment` 2407/**2419 `std::fs::write`**, `reply_context` 3670,
`reply_all_context` 3763, `forward_context` 3833, `flush_outbox` 3956,
`sync_apres_geste` 4058, `fetch_source_attachment` 5170-5245,
`sync_drafts` 5299, `backfill_bodies` 5967, `telecharger_et_lancer` 6269.
None of them holds `AppState.commandes`: `mark_flagged` under the lock
crosses with `message_body` outside the lock.
**Remedy**: extend the guard (the body of an `async` command = only
`hors_pompe(`/`spawn_blocking(` + glue; any `Store::open`, `lock_accounts`,
`std::fs`, `auth_for` outside it = FAILURE), prove it RED, migrate the 17.

### S1-3 · `open_link` launches `powershell.exe` synchronously on the main thread
`commands.rs:6136-6145` (exempted as "detached ShellExecuteW");
`apps/desktop/Cargo.toml:58` `open = "5"` without a feature. Verified
in `open-5.4.1/src/windows.rs:75`: `Command::new("powershell.exe")` +
`Start-Process`; `ShellExecuteW` only exists under
`shellexecute-on-windows`. A PowerShell `CreateProcess` (+ Defender)
on every link click, on the pump (150 ms budget).
**Remedy (1 line)**: `open = { version = "5", features = ["shellexecute-on-windows"] }`,
then measure with `freeze-probe.py`. Fix comment 6133 and `main-thread-guard:48`.

### S1-4 · No single-instance guard even though `main.rs:96-97` names the risk
The `outbox_flush`/`drafts_push`/`bodies_backfill` locks are per
process; no `tauri-plugin-single-instance` (verified). Double launch =
two flushes, two sets of IDLE watchers, double notification bubbles,
two `update_install` (the NSIS installer relaunches with `/R`).
**To confirm**: launch the exe twice, send a message.
**Remedy**: single-instance plugin (focus the existing window), or an
`fs4` file lock already a dependency, next to `wind.db`.

### S1-5 · IDLE watch: two unbounded reads per round
`crates/mail-imap/src/lib.rs:478-493` (`veiller`); verified in
`imap-3.0.0-alpha.15/src/extensions/idle.rs:225-247`: `init()` (sends
`IDLE`, reads the `+`) precedes setting the timeout, the exit does
`set_read_timeout(None)`, then `Drop → terminate()` reads the `DONE`
response **with no bound**. The doc-comment lib.rs:466-476 ("all reads
bounded") is contradicted. On a server/NAT that ACKs without
answering, the watcher thread freezes with no error and no reconnect
(ADR 0018 measured the DROP, not the acknowledged silence).
**Proof**: a local listener that answers `+ idling` then goes silent.
**Remedy**: keep a `TcpStream::try_clone()` before the TLS wrap and
re-set `set_read_timeout(Some(IO_TIMEOUT))` both on entry AND on exit
of `veiller` (socket options shared by the clone).

### S1-6 · Emptied mailbox = "initial" sync: zero notification, full re-download
`sync.rs:99` `if state.last_uid == 0 { initial_sync }`; `sync.rs:106`
`last_uid = max_uid`; `store.rs:3639` `COALESCE(MAX(uid), 0)`. INBOX
archived down to zero → next poll in `SyncMode::Initial` →
`notify.rs:50` bubbles nothing; `initial_sync` re-pays `list_uids` +
a full fetch. The `sync.rs:732` test freezes the mechanism without
seeing the consequence.
**Test (6 lines)**: add(1) → sync → expunge(1) → sync → add(2) → sync
⇒ `mode == Incremental`. **Remedy**: decide Initial on "state created
in THIS call" (`synced_once` flag), never on `last_uid == 0`.

### S1-7 · One refused action forever blocks a mailbox's log for life, silently
`sync.rs:229` `Err(_) => break`; `pending_actions` with neither
`attempts` nor `last_error` (`store.rs:141-146`); `error.rs:13`
`Server(String)` with no Transient/Permanent (the distinction exists
for SMTP, `transport.rs:17-29`). A `MoveTo` to a deleted folder fails
every cycle, holds back ALL of the mailbox's subsequent actions,
`SyncReport` has no error field, `faut_relever` (`sync.rs:395`) forces
the poll every cycle forever. The opposite of the Phase 2 gate
(`action.rs:3-6`).
**Remedy**: `attempts` + a `refusee` state (the `outbox.rejected`
pattern), error surfaced in `SyncReport`, `Error::Server { kind, detail }`.
Related: **store.rs:2061-2067** one unreadable `pending_actions` row
(unknown `kind`) fails ALL of `pending_actions(mailbox_id)`.

### S1-8 · CI does not run the example tests, including the one for credential non-disclosure
`.github/workflows/ci.yml:43` `cargo test --workspace` (without
`--all-targets`) vs `.githooks/pre-push:81-89`, which explains why
`--all-targets` "is NOT decorative". The one net that cannot be
bypassed (`--no-verify`) checks less than the hook. **Remedy (1 line)**:
`cargo test --workspace --all-targets` (+ `--doc`).

### S1-9 · The hook swallows the diagnostics of the three text gates
`.githooks/pre-push:58,63,70` `> /dev/null` while the `ECHEC …`
lines go to stdout (`contrast.mjs:111`, `system-coherence.mjs:42`,
`main-thread-guard.mjs:71`). `gate.ps1:5` says the opposite.
**Remedy**: remove the three redirections.

### S1-10 · `reset_mailbox` and `remove_local` non-atomic: phantom threads on crash
`store.rs:1455-1522` (9 autocommit DELETE/UPDATE then
`thread::rebuild_account`), `store.rs:1968-2005` (7 autocommit DELETE +
`thread::refresh` outside `echo.rs`); callers not wrapped:
`sync.rs:69`, `store.rs:1835-1837` (N×8 fsync per UID),
`store.rs:3532-3536`. A crash between DELETE and rebuild = `threads`
with `inbox_size > 0` and no envelopes: the "badge in front of an
empty list" already paid for at E5. **Remedy**: `unchecked_transaction`
like `save_body_full` (S:2124); `remove_local` requires the caller's
transaction. Test: fault injection in `rebuild_account` then
`unified_count == page.len()`.

### S1-11 · D-36 (phantom `echos` column) hits every NEW beta database
`store.rs:272`: `\n` in a `--` comment of the `SCHEMA` literal.
Already logged, but the five databases of wave 1 are born with it.
**Remedy**: one character. Test: `echos` column names on a fresh
database.

## 2. S2 findings — real bugs, perf, fragility

### 2.1 Core (`mail-core`)

- **Non-resumable initial sync** — `sync.rs:117-139`: a failure at
  batch k starts over from zero (`update_state` only after success). On
  a throttled Gmail full sync (D-17), hours replayed. Remedy: remove
  the UIDs already in the database before `chunks`.
- **Without CONDSTORE, flags never resync** —
  `sync.rs:174-175` promises a "full resync" that does not exist
  (only the UIDVALIDITY change does, `sync.rs:68`). Pinned by
  `sync.rs:864`. **[CE decision]**: bounded `FETCH FLAGS` window, or an
  explicit debt "first non-CONDSTORE account in beta".
- **`References: None` stored as "read, empty"** — `backfill.rs:285`
  `unwrap_or_default()` against `remote.rs:54-56`; `test_support.rs:238`
  never returns `None`: path not covered. To confirm on
  `fetch_thread_headers`.
- **`canonical_folders` swallows every SQLite error** — `nav.rs:174`
  `.unwrap_or(None)`: locked database = "no Sent", threads not
  reattached. Remedy: `.optional()?`.
- **`[Gmail]` hardcoded** — `nav.rs:119`: a `[Google Mail]/…`
  account (UK/DE) loses Archive/Spam/Trash; spammers get into the
  address book (`correspondants.rs:106`). To confirm; remedy:
  SPECIAL-USE carried by `Folder` (`remote.rs:105` has neither
  delimiter nor attributes).
- **SEND echo swept on the very first pass** — `echo.rs:351-355`
  (`origin_action_id IS NULL` always matches). To confirm on
  `commands.rs:4316`. Test: `echo_envoi` then `balayer_echos` with no
  poll of Sent ⇒ the echo survives.
- **An address in angle brackets taken for a Message-ID** —
  `thread.rs:65-73` + `:111-113`: `In-Reply-To: … <alice@x.fr>` merges
  unrelated threads (ADR 0008 to the letter, not the spirit). Remedy:
  reject a token equal to `sender/to/cc`.
- **`search_capped` counts on every keystroke** — `search.rs:295`
  unconditional against its own doc `:414-416`; `COUNT … MATCH` on a
  3-letter prefix = 36 k rows per character. Remedy: page first, COUNT
  only if `rows == limit`.
- **Outbox: unbounded poisoning** — `outbox.rs:544-548` Transient ⇒
  retries for life, blocks the account's queue; `attempts` is never
  read to decide. Remedy: N attempts ⇒ "to be decided".
- **Attachment bytes loaded for `is_empty()` and for the list** —
  `outbox.rs:327-347` + `commands.rs:4383,4453`: 25 MB × N re-read every
  cycle. Remedy: `outbox_pending_count`, `bytes` only at `flush`.
- **N+1 `canonical_folders`** — `echo.rs:330-336` (per echo),
  `correspondants.rs:99-113` (per `upsert_envelopes`), `nav.rs:808-832`
  (one query per threadless row, page of 200). Remedy: per-account
  cache invalidated on `folders` write; `IN` for the rows.
- **Four in-memory copies of the body at indexing** — `search.rs:613-637`:
  ~110 MB for a 28 MB body (D-1) on every `save_body`.
- **`Store::open` replays schema + 17 `table_xinfo` + migrations on
  EVERY open** — `store.rs:886-971`, ×107 sites in the shell, including
  the 5 s/10 s probes (~60 guard queries per command under the global
  lock; 2 740 ms cold at the `commands.rs:5823` milestone). Simplest
  remedy: a fast gate `PRAGMA user_version == SCHEMA_VERSION` ⇒ return;
  then a shared connection in `AppState` (D-9/D-34).
- **`upsert_envelopes` re-reads the whole HTML per re-synced envelope**
  — `store.rs:1796-1813`: 500 CONDSTORE deltas = ~28 MB re-read and
  re-tokenized under the write lock. Remedy: index only if new or if
  subject/sender/recipients changed.
- **`pending_actions` with no `(mailbox_id, uid)` index** — probes
  `store.rs:1189,1705,2054,3505`; in `nettoyage_verdict` the table
  grows while being scanned (quadratic, `3503-3511`).
- **`nettoyage_verdict`: `thread::refresh` + `deindex` per MESSAGE** —
  `store.rs:3532-3536`; the `touched: BTreeSet` pattern from S:1824 is
  not reused.
- **`nettoyage_groupes` / `portier_attente` unbounded** —
  `store.rs:3396-3427`, `3179-3210` (measurement due: real 200 k
  database).
- **`preview_catchup` loads 2 000 full bodies into RAM** —
  `store.rs:2306-2312`, shell 2317: ~112 MB at the 56 KB average,
  against the 200 MB budget (D-2). To confirm by RSS.
- **`boites_du_perimetre`: N+1 + `prepare` inside the loop** —
  `store.rs:3256-3291`, replayed 4 times per Cleanup session.
- **`migrate()`: non-transactional repairs, full `bodies` scans
  outside the migration screen** — `store.rs:4122,4137-4142,4161,
  4227-4241`; `filter_map(Result::ok)` at `4132,4224` sets the
  "repaired" marker even on unreadable rows. `pending_adoption`
  (`:780`) has no `busy_timeout` unlike its sibling `:861-865`.
- **Three divergent purge lists** — `remove_local` (7 tables),
  `reset_mailbox` (8), `remove_absent` (**3**, `store.rs:1942-1956`): a
  message deleted server-side leaves `attachments`, `invitations`,
  `images_messages`, `mis_de_cote`, `kiosque_lus` orphaned (no FK).
  Remedy: ONE `purger_message(conn, mailbox_id, uid)`.
- **`set_thread_scope`, `set_recipients` non-atomic** —
  `store.rs:1268-1276`, `2523-2546`.
- **`rattraper_correspondants`: raw `BEGIN IMMEDIATE` + `let _ = ROLLBACK`**
  — `correspondants.rs:203,296,300`: a failed ROLLBACK leaves the
  connection in a transaction. Remedy: `unchecked_transaction`.
- **`Error::Server(String)` with no classification** — `error.rs:13`:
  the root of S1-7; SMTP has it (`transport.rs`).

### 2.2 Adapters

- **SMTP: 535 mid-flush ⇒ `Permanent` ⇒ message rejected** —
  `mail-smtp/src/lib.rs:8-11` (doc) vs `lettre` with no `pool` feature
  (every `send` reopens and re-authenticates, `transport.rs:53-60`) and
  `lib.rs:120` every 5xx ⇒ Permanent. Remedy: 530/534/535/538 ⇒
  `Transient` (1 `match` on `err.status()`).
- **`References` truncated to the parent** — `mail-smtp lib.rs:206-208`:
  RFC 5322 §3.6.4 wants the chain; our sends break threads at the
  recipient's end and in our own re-read Sent. Remedy:
  `OutboxMessage.references` filled by `compose`.
- **SMTP with no network/auth discriminant** — `lib.rs:95-107`
  everything ⇒ Transient; the shell does `Err(_) => refresh`
  (`commands.rs:5466`): every network outage hammers the OAuth
  endpoint (the P0 flaw fixed on the IMAP side only).
- **Renewed refresh token discarded** — `mail-auth/src/lib.rs:183-185`
  (`store_refresh: None`): Azure AD returns a new token, the old one
  expires at 90 days ⇒ delayed silent disconnection (mirrors D-44).
  One-line spike to confirm. Remedy: 3 lines.

  `flow.rs:193-218` (`incoming()` blocking, `read_line` with no
  timeout, the final `Err` unreachable), `flow.rs:111-113` (the

- **`Debug` derived with the secrets included** — `mail-auth lib.rs:39,49,63`

  masked `impl Debug`.
- **UIDPLUS never checked** — `mail-imap lib.rs:534-542`: on a server

- **`delete`/`archive` from Gmail Trash/Spam = destruction** —

  the trash).
- **`changes_since` unbounded** — `lib.rs:617-622` `UID FETCH 1:* …
  CHANGEDSINCE`: after a long offline stretch, the whole mailbox in one
  response. Remedy: UIDs first, envelopes in batches.
- **`Reply-To`/`Sender` discarded** — `convert.rs:196-241`: "Reply"
  goes to `From` even when `Reply-To` is set. Remedy: a field in
  `Envelope`.
- **`HEADER.FIELDS` works but is not used** — `lib.rs:573-598` (doc
  contradicted by `imap-proto body.rs:21-25`): ×10-20 the bytes on
  `THREAD_HEADER_BATCH = 200`. Remedy: one string.
- **Raw body parsed 2-3 times per message** — `lib.rs:904-921`

- **`fetch_bodies_html`: 50 whole messages in RAM with no size
  bound** — `lib.rs:648-671` (worst case > 1 GB). Remedy:
  `RFC822.SIZE` first, batches ≤ 32 MB.
- **`decode_header` launches a full `MessageParser` per subject and
  per name** — `convert.rs:638-653`, 2 × 500 per batch.
- **Attachment rank = a function of the adapter's code** —
  `convert.rs:537-562`: any filter change shifts the stored ranks

- **iCal: first VEVENT taken as-is** — `mail-ical lib.rs:140-144`: a
  CANCEL of ONE occurrence (`RECURRENCE-ID`) cancels the whole series
  on screen. `DURATION` with no `DTEND` ⇒ `fin: None` (`:203-205`).
- **Rendering: `img-src http:` in `AllowRemote`, no `no-referrer`** —

- **Three TLS stacks in one Windows binary** — `native-tls` (IMAP,

- **Already D-17**: `is_connection_error` too narrow.

## 4. Architecture patterns

1. **"One brain" upheld at the SQL level (0 `rusqlite` in the
   shell, 0 `invoke` outside the port), breached at the POLICY level.** An
   account's sync engine is `run_sync` (313 l.) in the shell;
   `frontiere_corps` ("THE rich-body boundary") lives in the shell;
   `vue_invitation` recomputes what the core already serves; 12 pure
   functions tested in-file in `commands.rs` (`attente_apres_echecs`,
   `safe_file_name`, `mime_for_name`, `repere_valide`, `nom_normalise`,
   `resoudre_categorie`…); the sync scheduler (cadences,
   watchdog, sleep, network) lives in `App.svelte`; the
   auth provider is guessed in JS (`GuichetCompte:47-50`); the
   text of an outgoing mail (iTIP reply) is built by the UI. The web
   version (Phase 4) will find none of this ready-made. → `mail-core::sync_account`,
   `releve.rs` (breaks the `veilleur` ↔ `commands` two-way coupling),
   a `tokio` scheduler on the shell side, `fournisseur(email)` on the core side.
2. **"Pure decision, execution elsewhere" (STANDARD §4) applied to
   the leaves, not to the trunk.** `plan_sync` does not exist (the
   initial/incremental/reset choice is inlined with `select` and `replay`) — a
   `plan_sync(state, snapshot) -> SyncPlan` would have made S1-6 testable in
   one line; `flush_outbox` is an inline state machine; `geste_avec_echo`
   buries its decision inside the transaction; the Screener's arrival decision
   and the Non rule are written STRAIGHT INTO the SQL loops (`store.rs:1677-1755`).
   Counter-examples worth copying: `thread::plan`, `plan_draft_pull`, `notify`,
   `crash`, `demenagement.rs`.
3. **`mail-core` is a `store.rs` spread thin.** Six "business" modules
   (`nav`, `echo`, `drafts`, `outbox`, `correspondants`, `search`) are
   `impl Store` + SQL in a cycle with the hub (`nav.rs:23-26` imports 9
   SQL fragments from `store`, `store.rs:1544,1560` calls back into `nav`/
   `correspondants`). The `MailServer` trait mixes capability and data
   (`Option<Vec>` = "not supported") and `Folder` has neither delimiter nor
   SPECIAL-USE (hence the guessed `[Gmail]`). → `store/` split into
   declared submodules so the `use` tree tells the truth; `capabilities()`
   separated out; `Folder { delimiter, special_use }`.
4. **One SQLite connection per command** (107 `Store::open` calls, the full
   ritual every time). The global `commandes` lock already serializes:
   a shared connection in `AppState` is the simplest form,
   and it removes D-9, D-34, and half of S2-core.
5. **Untyped error policy at the network port** — `Error::Server(String)`,
   `SendError::Transient(String)` catch-all, 332 `map_err → String` in
   the shell: neither replay (S1-7), nor OAuth refresh (SMTP hammers
   the endpoint), nor the UI can make a decision.
6. **The UI is a controller**: `App.svelte` orchestrates via 10
   `bind:this` and 20 imperative methods; any view App does not hold
   is never re-served (D-48). A `generation` store is the simplest
   fix.
7. **Three TLS stacks** and **two `reqwest`s** in one Windows binary.
8. **The text-based gates keep keywords, not properties**:
   `main-thread-guard` stops at `async`; `startup.spec` ignores
   missing probes; the `__e2e*` seams live in prod.

## 5. Action plan

Order: first what protects (PII, data, main thread), then
what makes the next bugs testable (error types, pure
decisions, shared connection), then cleanliness — **at the first
