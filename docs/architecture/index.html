Wind Architecture

The mail client of the Elements suite: Rust core, Svelte interface, packaged with Tauri. "Your mail, instantly."

Version 0.1.8 Windows native arm64 5 crates + desktop shell Rust edition 2024 · 1.97.1 Svelte 5 · Tauri 2 SQLite WAL + FTS5 20 frozen ADRs

This document formalizes the state of the architecture at version 0.1.8. It is derived from the code and the frozen decisions (docs/adr/, docs/HANDOVER.md). The source of truth remains the code; this page is the map, not the territory.

§0 Executive summary

One principle organizes everything else: a single brain. All the logic lives in a portable Rust core; the interface is "dumb".

A single brain

mail-core carries 100% of the domain, the sync, the storage, the search and the threads — zero UI or network dependency. The desktop embeds it in-process; the web (Phase 4) will run it server-side, without touching it.

A single boundary

The core knows only two abstract ports: MailServer (read) and MailTransport (send). IMAP, SMTP, OAuth and TLS live in adapters. SQLite, on the other hand, is not behind a trait — a frozen decision.

Performance is the feature

Startup < 1 s (337 ms measured), opening < 50 ms (1–3 ms), list page < 100 ms (0.58 ms) at 200,000 messages. A budget overrun stops the line (andon).

Reliable & safe

Never a loss, never a phantom send (log before network, quarantine). Credentials in the OS vault, HTML sanitized in depth, remote images blocked.

Complete & offline

The whole mailbox is local and searchable — 256,312 messages on the reference mailbox, junk and trash included. Reading, sorting, searching, writing all work without network.

The window never freezes

No blocking command on the message-pump thread: everything goes through off_pump(). 25.2 s of cumulative freezes → 0, held by a guard and a probe.

What Wind is not (v1)

No calendar, no chat, no built-in AI, no plugins, no mobile. Saying no is the default behavior: every addition is paid for in speed and reliability.

§1 Overview

Five layers, one direction of flow: the interface emits intents downward, state flows back up. The only abstract boundary is the line of ports.

The same core serves two targets. On the desktop, the UI's transport port is an in-process implementation that calls the Tauri IPC. In Phase 4, the web will replace this hop with a POST /api/call/<command> to mail-core running server-side — without changing the app. The seam is already written in transport.js.

§3 mail-core, the brain

The core knows neither Tauri, nor the web, nor IMAP. It answers questions and makes decisions; I/O lives elsewhere. This is the recurring pattern that makes the field testable without a network.

The pattern: pure decision, execution elsewhere

Wherever possible, the decision is a pure, testable function; the execution (I/O, network) is kept separate. This split makes it possible to replay field scenarios — a temperamental server, a legacy database, a 250,000-message mailbox — without ever opening a socket.

§4 The two ports

The whole abstract boundary of the core fits in two traits. The rest (SQLite) is concrete and owned as such.

Frozen decision

SQLite is NOT behind a trait. Store is a concrete struct; tests use an in-memory database; the journal is WAL on file (ADR 0011). Abstracting storage would have cost something and proven nothing — the core is already independent from everything that matters.

§5 Data model

A single SQLite database, in WAL, with its indexes and aggregates inside the database — maintained in the same transaction as the message. A message's identity is (account_id, mailbox, uid) everywhere.

Storage invariants

  • Indexes and aggregates inside the database: FTS5 and the threads table are maintained in the same transaction as the message.
  • Store everything, group only the scope: a message outside INBOX + Sent keeps thread_id = NULL forever (mailboxes.threaded + accounts.sent_mailbox). Without this, a spam message latched onto a thread would bump it to the top of the list.
  • Adopting migrations: a new feature adopts the old data, proven by a test that rewinds a real file database (PRAGMA user_version). The trap has struck four times.
  • UIDVALIDITY: if it changes, the mailbox starts over from zero and the whole account rebuilds its threads (thread::rebuild_account).

Data at rest

The database lives at %APPDATA%\dev.elements.wind\wind.db with its two WAL companions (-wal, -shm) — a hot copy takes all three. The "database < 1 GB" budget is lifted (ADR 0010): the database grows to ~13 GB (256,312 × ~50 KB) and it's the disk-space guard that watches before each commit.

§6 Synchronization

"Envelopes first": the list becomes usable from the very first batch, the rest (bodies, thread headers, recipients) is backfilled in the background. Everything is synchronized, with no horizon and no quota (ADR 0010).

Envelopes first

Initial sync from most recent to oldest, in batches of 500. In-Reply-To comes free from the ENVELOPE; References requires a separate pass (10× larger).

Incremental

CONDSTORE (RFC 7162) when the server exposes it — new messages AND flag changes via HIGHESTMODSEQ. Otherwise, a UID diff.

Poll coalescing

One poll lock per account: cycle, button and watcher can all target the same INBOX — only one pays, the others wait.

Anti-hammering

A failing account accumulates a backoff (consecutive failures, in memory); the cycle skips it without hiding it. A manual gesture always forces the attempt.

§7 Conversations

Grouping is a union-find over RFC 5322 identifiers. Never a subject-based fallback; an identifier requires an at-sign (ADR 0008).

Why "References" matters

In an inbox, the middle message of an exchange is often the one you sent yourself — it isn't in INBOX. Without References (fetched in the background), half of the conversations would stay cut in two. The pieces stitch back together as soon as the link appears, without loss.

§8 Outbox & echoes

The two golden rules (ADR 0003): never a lost send, never a phantom send. "A duplicate is worse than a delay."

Never lost

The intent enters the database before the first network byte. A crash during send leaves a queued row that gets replayed.

Never a phantom

A permanent refusal goes to quarantine. No automatic resend: a duplicate is worse than a delay.

Serialized

An outbox_flush lock: two concurrent pumps would quarantine each other's sends.

Gesture echoes

Delete, archive and send each have their own destination echo (sent/archive/trash) — never in envelopes (a made-up UID would forge the key).

§9 Tauri shell & IPC

The desktop shell wires the Tauri window to the core. It carries the shared state (locks, watchers, progress) and exposes ~55 commands to the UI.

The IPC surface

The UI never calls a privileged Tauri API directly: it goes through our commands (least privilege). Notifications and the updater are driven from Rust; the one exception is the file picker (dialog:allow-open).

The shared state (AppState)

Serialization locks

outbox_flush, drafts_push, bodies_backfill, and poll_locks (one per account): keep two concurrent passes from fighting over the same messages.

Shared progress

MigrationShared and SyncShared: atomics, not Mutexes — the pass writes, polling must never make it wait.

Watchers & network

watchers (per-account life flag), online, sync_backoffs, gesture_passes (coalesced).

The global lock

commands: the key of off_pump() — one blocking command at a time, just as when the main thread used to serialize them (§10).

Before everything else

At startup, main() first runs the Discovery → Wind relocation: neither the database nor the WebView2 profile may be born on the Wind side while a Discovery workstation is waiting for its rename. Failure = hard stop. Then the telemetry hook installs (without touching the database), and the window starts.

§10 Thread model

In Tauri 2, a command without async runs on the main thread — the Windows message pump. A single slow request freezes the window there. The answer: everything that blocks leaves the pump (ADR 0019).

§12 Svelte interface

A single web front end (Svelte 5), meant to be ported everywhere: Tauri desktop today, mobile and browser tomorrow (ADR 0015). The visual System is written once.

Screen components

App orchestrates. Nav, List, Reading/Thread, Conversation, Compose, Settings, Onboarding, AccountDesk, MigrationModal.

Reactive state ($state)

Modules thread.svelte.js, widths.svelte.js, text.svelte.js, panes.svelte.js — the state lives in the store, never in local booleans reconciled by hand.

The thread: one object, two frames

Frame exclusivity (thread.frame: null / pane / full) lives in the store. Every clear goes through closeThread().

3 layout modes

Three panes (default), two panes, or one pane with a drawer nav. Boundaries adjustable with the mouse (pointer capture).

28 "Wada" themes

14 light + 14 -night variants, 119 tokens in system.css, choice persisted in localStorage.

Language — homegrown catalog

catalog.fr.js / catalog.en.js (ADR 0016). The language is read without adopting the database (invariant A41).

Platform trap

prefers-color-scheme is dead in Tauri's WebView2: never dark, zero event, even under a real Windows toggle. Listening for the OS theme goes through the Tauri window API (theme() + onThemeChanged); matchMedia is only the fallback outside Tauri. Scrollbars are native overlays, set by additionalBrowserArgs.

§13 Delivery & quality

Nothing leaves the machine without the full gate. Delivery is an NSIS installer and a minisign-signed update (ADR 0013).

E2E determinism

The e2e tests drive the real Tauri window via CDP WebView2 (Playwright). Sealed by construction: a disposable database (WIND_DB_PATH), fake accounts (WIND_E2E_ACCOUNT), a dedicated WebView2 profile, a free CDP port per suite (two suites running at once no longer collide). They talk to no server: the whole real network path is only proven in the field.

Visible & interruptible migration (ADR 0012)

Adopting a legacy database is a single transaction — from the conditional DROP of the thread tables to PRAGMA user_version. Canceling rewinds everything and leaves user_version unchanged: never a partial adoption, the pass replays whole on the next launch. A modal screen at startup; nothing touches the database before migration_check (invariant A41).

Budgets are blocking gates: an overrun stops the line. Debt is carried knowingly — every deferral is a motivated line item.

Technical debt (excerpt from the register)

  • D-1 — Opening p95 (52–55 ms) above budget on very large bodies (> 1 MB): HTML sanitization cost. Lead: lazy/streaming sanitization.
  • D-8 — Expensive periodic probes off the pump (nav_snapshot 865 ms, pending_total 575 ms): no longer freeze anything, but the CPU cost is real. Lead: generation-invalidated cache.
  • D-9 — Invariant A41 ("nothing touches the database before migration_check") has no structural guard, only a probe test.
  • Cross-mailbox duplicates in search (a message copied into several mailboxes surfaces several times) — to observe in beta before deciding on deduplication.

Where Wind goes next

The last step before gate 5 is the closed beta of 20–50 users, with weekly kaizen on observed friction. Gate 5: two weeks with no critical defect. Phase 4 (web) will reuse the core intact, behind the remote transport port.
