Architecture de Wind

Le client courrier de la suite Elements : cœur Rust, interface Svelte, empaqueté par Tauri. « Vos mails, instantanément. »

Version 0.1.8 Windows arm64 natif 5 crates + shell desktop Rust edition 2024 · 1.97.1 Svelte 5 · Tauri 2 SQLite WAL + FTS5 20 ADR gelés

Ce document formalise l'état de l'architecture à la version 0.1.8. Il est dérivé du code et des décisions gelées (docs/adr/, docs/PASSATION.md). La source de vérité reste le code ; cette page en est la carte, pas le territoire.

§0 Résumé exécutif

Un principe organise tout le reste : un seul cerveau. Toute la logique vit dans un cœur Rust portable ; l'interface est « bête ».

Un seul cerveau

mail-core porte 100 % du domaine, de la synchro, du stockage, de la recherche et des fils — zéro dépendance UI ou réseau. Le desktop l'embarque en processus ; le web (Phase 4) l'exécutera côté serveur, sans le toucher.

Une seule frontière

Le cœur ne connaît que deux ports abstraits : MailServer (lecture) et MailTransport (envoi). IMAP, SMTP, OAuth et TLS vivent dans des adaptateurs. SQLite, lui, n'est pas derrière un trait — décision gelée.

La performance est la fonctionnalité

Démarrage < 1 s (337 ms mesurés), ouverture < 50 ms (1–3 ms), page de liste < 100 ms (0,58 ms) à 200 000 messages. Un budget dépassé arrête la ligne (andon).

Fiable & sûr

Jamais de perte, jamais d'envoi fantôme (journal avant réseau, quarantaine). Credentials au coffre de l'OS, HTML assaini en défense en profondeur, images distantes bloquées.

Complet & hors-ligne

Toute la boîte est locale et cherchable — 256 312 messages sur la boîte de référence, spam et corbeille compris. Lire, trier, chercher, écrire fonctionnent sans réseau.

La fenêtre ne gèle jamais

Aucune commande bloquante sur le thread de la pompe de messages : tout passe par hors_pompe(). 25,2 s de gels cumulés → 0, tenu par une garde et une sonde.

Ce que Wind n'est pas (v1)

Pas de calendrier, pas de chat, pas d'IA intégrée, pas de plugins, pas de mobile. Dire non est le comportement par défaut : chaque ajout se paie en vitesse et en fiabilité.

§1 Vue d'ensemble

Cinq couches, un sens de circulation : l'interface émet des intentions vers le bas, l'état remonte vers le haut. La seule frontière abstraite est la ligne des ports.

Le même cœur sert deux cibles. Sur le desktop, le port de transport de l'UI est une implémentation en processus qui appelle l'IPC Tauri. En Phase 4, le web remplacera ce rejet par un POST /api/appel/<commande> vers mail-core exécuté côté serveur — sans changer l'application. La couture est déjà écrite dans transport.js.

§2 Le workspace

Un workspace Cargo multi-crates (ADR 0001). Les dépendances ne remontent jamais vers l'UI : mail-core est la racine, tout converge vers lui.

Discipline de crate

unsafe_code = "forbid" sur tout le workspace. unwrap()/expect() en warn (donc rouge au gate, clippy -D warnings). Erreurs typées (thiserror) dans les crates, anyhow dans les apps. Rust épinglé à 1.97.1 (rust-toolchain.toml) — source unique, alignée local / hook / CI.

§3 mail-core, le cerveau

Le cœur ne connaît ni Tauri, ni le web, ni IMAP. Il répond à des questions et prend des décisions ; l'I/O vit ailleurs. C'est le motif récurrent qui rend le terrain testable sans réseau.

Le motif : décision pure, exécution ailleurs

Partout où c'est possible, la décision est une fonction pure et testable ; l'exécution (I/O, réseau) est séparée. Ce découpage permet de rejouer les scénarios du terrain — un serveur capricieux, une base héritée, une boîte de 250 000 messages — sans jamais ouvrir de socket.

thread::plan

À quel fil rattacher un message ? Union-find pur sur les en-têtes RFC 5322.

sync_order · sync_percent

Dans quel ordre relever les boîtes ; où en est l'avancement (dénominateur = EXISTS).

disk_shortfall

Combien d'espace il manque avant de s'engager — la garde de l'ADR 0010, pure.

plan_draft_pull

Que tirer du dossier Brouillons distant ? Détection de conflit d'édition.

convert::sent_folder

Quel dossier est celui des envois, à partir des attributs LIST.

notify::arrivals_to_notify

Quelles arrivées méritent une bulle — et dans quelle langue.

Outillage de diagnostic (lecture seule, aucun contenu divulgué)

Trois diagnostics (diagnostic_index, diagnostic_fils, diagnostic_brouillons), trois bancs (banc_page_liste, banc_migration_fils, banc_recherche) et seed_inbox vivent dans crates/mail-core/examples/. Ils mesurent le terrain sans jamais exposer un sujet, un expéditeur ou un identifiant en clair.

§4 Les deux ports

Toute la frontière abstraite du cœur tient en deux traits. Le reste (SQLite) est concret et assumé.

Décision gelée

SQLite n'est PAS derrière un trait. Store est une struct concrète ; les tests utilisent une base en mémoire ; le journal est en WAL sur fichier (ADR 0011). Abstraire le stockage aurait coûté sans rien prouver — le cœur est déjà indépendant de tout ce qui compte.

§5 Modèle de données

Une base SQLite unique, en WAL, avec ses index et agrégats dans la base — entretenus dans la même transaction que le message. L'identité d'un message est (account_id, boîte, uid) partout.

Invariants du stockage

  • Index et agrégats dans la base : FTS5 et la table threads sont entretenus dans la même transaction que le message.
  • Stocker tout, ne regrouper que la portée : un message hors de INBOX + Envoyés garde thread_id = NULL pour toujours (mailboxes.threaded + accounts.sent_mailbox). Sans quoi un spam accroché à un fil le ferait remonter en tête de liste.
  • Migrations adoptantes : une fonctionnalité neuve adopte les données anciennes, prouvée par un test qui rembobine une vraie base de fichier (PRAGMA user_version). Le piège s'est présenté quatre fois.
  • UIDVALIDITY : si elle change, la boîte repart de zéro et tout le compte refait ses fils (thread::rebuild_account).

Données au repos

La base vit dans %APPDATA%\dev.elements.wind\wind.db avec ses deux compagnons WAL (-wal, -shm) — une copie à chaud prend les trois. Le budget « base < 1 Go » est levé (ADR 0010) : la base grandit vers ~13 Go (256 312 × ~50 ko) et c'est la garde d'espace disque qui veille avant chaque engagement.

§6 Synchronisation

« Enveloppes d'abord » : la liste devient utilisable dès le premier lot, le reste (corps, en-têtes de fil, destinataires) se rattrape en tâche de fond. Tout est synchronisé, sans horizon ni quota (ADR 0010).

Enveloppes d'abord

Synchro initiale du plus récent au plus ancien, par lots de 500. In-Reply-To vient gratuitement de l'ENVELOPE ; References exige une passe séparée (10× plus gros).

Incrémentale

CONDSTORE (RFC 7162) quand le serveur l'expose — nouveaux messages ET changements de flags via HIGHESTMODSEQ. Sinon, différentiel d'UIDs.

Coalescence des relèves

Un verrou de relève par compte : cycle, bouton et veilleur peuvent viser le même INBOX — un seul paie, les autres attendent.

Anti-martèlement

Un compte en échec accumule un recul (échecs consécutifs, en mémoire) ; le cycle le saute sans le taire. Le geste manuel force toujours la tentative.

§7 Conversations

Le regroupement est un union-find sur les identifiants RFC 5322. Jamais de repli par sujet ; un identifiant exige une arobase (ADR 0008).

Pourquoi « References » compte

Dans une boîte de réception, le message intermédiaire d'un échange est souvent celui qu'on a soi-même envoyé — il n'est pas dans INBOX. Sans References (rapatrié en tâche de fond), la moitié des conversations resterait coupée en deux. Les morceaux se recollent dès que le lien apparaît, sans perte.

§8 Boîte d'envoi & échos

Les deux règles d'or (ADR 0003) : jamais d'envoi perdu, jamais d'envoi fantôme. « Le doublon est pire que le retard. »

Jamais perdu

L'intention entre en base avant le premier octet réseau. Un crash pendant l'envoi laisse un queued qui se rejoue.

Jamais fantôme

Un refus permanent met en quarantaine. Aucun renvoi automatique : le doublon est pire que le retard.

Sérialisé

Un verrou outbox_flush : deux pompes concurrentes mettraient en quarantaine les envois l'une de l'autre.

Échos de geste

Suppression, archivage et envoi ont leur écho de destination (envoyés/archives/corbeille) — jamais dans envelopes (un UID inventé forgerait la clé).

§9 Shell Tauri & IPC

Le shell desktop branche la fenêtre Tauri sur le cœur. Il porte l'état partagé (verrous, veilleurs, avancement) et expose ~55 commandes à l'UI.

La surface IPC

L'UI n'appelle jamais une API Tauri privilégiée directement : elle passe par nos commandes (moindre privilège). Notifications et updater sont pilotés depuis Rust ; seule exception, le sélecteur de fichiers (dialog:allow-open).

L'état partagé (AppState)

Verrous de sérialisation

outbox_flush, drafts_push, bodies_backfill, et verrous_releve (un par compte) : empêchent deux passes concurrentes de se disputer les mêmes messages.

Avancement partagé

MigrationShared et SyncShared : des atomiques, pas des Mutex — la passe écrit, le sondage ne doit jamais la faire attendre.

Veilleurs & réseau

veilleurs (drapeau de vie par compte), en_ligne, sync_reculs, passes_geste (coalescées).

Le verrou global

commandes : la clé de hors_pompe() — une commande bloquante à la fois, comme quand le thread principal les sérialisait (§10).

Avant tout le reste

Au démarrage, main() exécute d'abord le déménagement Discovery → Wind : ni la base ni le profil WebView2 ne doivent naître côté Wind pendant qu'un poste Discovery attend son renommage. Échec = arrêt net. Puis le hook de télémétrie s'installe (sans toucher la base), et la fenêtre démarre.

§10 Modèle de threads

Dans Tauri 2, une commande sans async s'exécute sur le thread principal — la pompe de messages Windows. Une seule requête lente y gèle la fenêtre. La réponse : tout ce qui bloque sort de la pompe (ADR 0019).

§12 Interface Svelte

Front web unique (Svelte 5), destiné à être porté partout : Tauri desktop aujourd'hui, mobile et navigateur demain (ADR 0015). Le Système visuel est écrit une fois.

Composants d'écran

App orchestre. Nav, Liste, Lecture/Fil, Conversation, Composition, Réglages, Onboarding, GuichetCompte, ModaleMigration.

État réactif ($state)

Modules fil.svelte.js, largeurs.svelte.js, texte.svelte.js, volets.svelte.js — l'état vit au store, jamais en booléens locaux réconciliés à la main.

Le fil : un objet, deux cadres

L'exclusivité des cadres (fil.cadre : null / volet / plein) vit au store. Toute purge passe par fermerFil().

3 modes d'affichage

Trois volets (défaut), deux volets, ou un volet avec nav en tiroir. Frontières réglables à la souris (capture du pointeur).

28 thèmes « Wada »

14 clairs + 14 déclinaisons -nuit, 119 jetons dans systeme.css, choix persisté en localStorage.

Langue — catalogue maison

catalogue.fr.js / catalogue.en.js (ADR 0016). La langue se lit sans adopter la base (invariant A41).

Piège de plateforme

prefers-color-scheme est mort dans le WebView2 de Tauri : jamais sombre, zéro événement, même sous une vraie bascule Windows. L'écoute du thème OS passe par l'API fenêtre Tauri (theme() + onThemeChanged) ; matchMedia n'est que le repli hors Tauri. Les barres de défilement sont natives en surimpression, posées par additionalBrowserArgs.

§13 Livraison & qualité

Rien ne quitte la machine sans la gate complète. La livraison est un installeur NSIS et une mise à jour signée minisign (ADR 0013).

Déterminisme des E2E

Les tests e2e pilotent la vraie fenêtre Tauri via CDP WebView2 (Playwright). Étanches par construction : base jetable (WIND_DB_PATH), comptes factices (WIND_E2E_ACCOUNT), profil WebView2 dédié, port CDP libre par suite (deux suites simultanées ne se marchent plus dessus). Ils ne parlent à aucun serveur : tout le chemin réseau réel ne se prouve que sur le terrain.

Migration visible & interruptible (ADR 0012)

L'adoption d'une base héritée est une seule transaction — du DROP conditionnel des tables de fils jusqu'à PRAGMA user_version. Annuler rembobine tout et laisse user_version inchangé : jamais d'adoption partielle, la passe se rejoue entière au prochain lancement. Écran modal au démarrage ; rien ne touche la base avant migration_check (invariant A41).

§15 Budgets & dette

Les budgets sont des gates bloquants : un dépassement arrête la ligne. La dette est assumée en connaissance — chaque report est une ligne motivée.

Dette technique (extrait du registre)

  • D-1 — Ouverture p95 (52–55 ms) au-dessus du budget sur les très gros corps (> 1 Mo) : coût d'assainissement HTML. Piste : assainissement paresseux / streaming.
  • D-8 — Sondes périodiques chères hors pompe (nav_snapshot 865 ms, pending_total 575 ms) : ne gèlent plus rien, mais le coût CPU reste réel. Piste : cache invalidé par génération.
  • D-9 — L'invariant A41 (« rien ne touche la base avant migration_check ») n'a pas de garde structurelle, seulement un test de sonde.
  • Doublons multi-boîtes dans la recherche (un message copié dans plusieurs boîtes remonte plusieurs fois) — à observer en bêta avant de décider d'un dédoublonnage.

Où va Wind ensuite

La dernière étape avant le gate 5 est la bêta fermée 20–50 utilisateurs, avec kaizen hebdomadaire sur les frictions observées. Gate 5 : deux semaines sans défaut critique. La Phase 4 (web) réutilisera le cœur intact, derrière le port de transport distant.
